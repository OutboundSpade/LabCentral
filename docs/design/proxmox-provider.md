# Proxmox provider foundation and gated QEMU mutation

`TASK-PROXMOX-001` implements target-scoped discovery in the separate `lab-provider-proxmox` process. `TASK-PROXMOX-004` adds the closed validation, planning, state, journal, apply, read, destroy, `GetInvocation`, and start/stop/pause/resume implementation for the accepted fixed-node Linux QEMU subset, plus its complete T0 fake-API suite. `TASK-PROD-003` adds qualified exact-resource VNC endpoint discovery for the separate noVNC access process. Image import, SSH access, cancellation, state migration, and every out-of-subset operation remain unimplemented.

The normal `NewService` constructor remains unconditionally discovery-only, and the package-private T0 constructor remains test-only. ADR-0014 adds the only exported write-capable constructor: it requires a non-nil `MutationAuthorizer`. The production executable selects it only when both a signed qualification document and deployment trust policy load successfully. Protocol v1.1 compatibility, `mutationEnabled`, discovery evidence, or signature validity by themselves never enable writes. The authorizer rebinds a passing artifact to the exact target/configuration, current live mutation inventory, PVE build, reviewed profile, running provider executable, embedded source tree, reviewer validity/revocation, and bounded evidence age on discovery and every mutation.

## Versioned envelopes

The plugin advertises discovery-compatible `proxmox.target-config` v1.0, additive target-config v1.1, API-token credentials v1.0, capacity v1.0, validation-plan v1.0, QEMU plan/state v1.0, and invocation-journal v1.0. JSON envelopes reject unknown or recursively duplicate fields, trailing JSON values, empty input, and oversized input.

Target configuration fields are:

| Field | Type/default | Constraint |
|---|---|---|
| `endpoint` | required string | HTTPS origin only, normally `https://pve.example:8006`; no user information, path, query, or fragment. |
| `caCertificatePEM` | optional PEM string | Adds one or more private CA certificates to system trust; invalid PEM is rejected. TLS verification is never disabled. |
| `requestTimeoutSeconds` | optional integer, default 10 | Maximum 30 seconds. |
| `maxResponseBytes` | optional integer, default 4 MiB | Between 1 KiB and 16 MiB for each upstream response. |

Mutation remains false by default. A v1.1 mutation target additionally fixes an installation ID, the exact supported PVE 9.x range and destination node/pool, disjoint VMID ranges, approved template aliases with SHA-1 config and SHA-256 content digests and cloned-disk inventory, storage aliases/formats, bridge aliases and VLAN pools, VM/NIC/compute limits, positive intended-segment and negative management/cross-instance probe evidence, exact-target qualification digests, non-root `0700` journal directory, and least-privilege ACL paths. The configuration rejects `/` write scope, missing privileges, `Sys.Modify`, and `VM.GuestAgent.Unrestricted`. The initial planner may select only those aliases; raw VMIDs, storage IDs, bridges, VLANs, QEMU fields, and force flags cannot come from Lab input.

The separate credential envelope has exactly `tokenID` and `tokenSecret`. `tokenID` uses `USER@REALM!TOKENID`; `tokenSecret` is the value Proxmox displays once when it creates the token. The provider constructs the documented `Authorization: PVEAPIToken=USER@REALM!TOKENID=UUID` header in memory for each request. It does not persist or log either envelope, include upstream error bodies in errors, or copy credentials into capability/capacity output.

## Discovery and evidence

One discovery invocation performs only these Proxmox JSON API `GET` requests:

1. `/version` and `/nodes` establish the target version and bounded node set.
2. For each node whose returned status is exactly `online`, `/nodes/{node}/storage?content=images&enabled=1&format=1` discovers enabled VM-image storage and formats.
3. `/nodes/{node}/network?type=bridge` discovers bridges, ports, and VLAN-awareness flags.
4. `/nodes/{node}/qemu?full=0` proves QEMU-list API reachability and discovers records explicitly marked as templates.

Provider-returned node names are validated before they enter a URL path. Node count, aggregate inventory items, nested items, field lengths, per-response bytes, and the final capacity document are bounded. Results are normalized and lexically sorted before a SHA-256 full-inventory digest is calculated. Offline nodes are retained as capacity facts but are not queried further. A node-level permission, availability, transport, response, or limit failure becomes a stable typed issue when the rest of the inventory remains usable.

`DiscoverTarget` returns `proxmox.capacity` v1.0 JSON containing the version, nodes, QEMU reachability, templates, storage content/formats/capacity, bridges, issues, and inventory digest. Capability evidence cites that digest, the observed Proxmox version, online-node count, and issue count. The target configuration fingerprint is included only when it is a canonical lowercase `sha256:` digest. Evidence expires after five minutes.

Discovery facts alone do not establish mutation support. `workload.vm` and supported lifecycle capabilities become native only when the pinned `proxmox.mutation-inventory/v1.0` digest, PVE 9.x node/template/storage/bridge facts, exact ACL paths, template config/forbidden-device checks, connectivity evidence, protocol-compatible configuration, durable journal, and ADR-0014 signed authorization all match. The mutation projection includes target/build identity, node availability and fixed capacity, storage identity/formats/total capacity, bridge ports/addressing/VLAN state, templates, and discovery issues; it excludes CPU load, used memory, uptime, and used/free storage counters so normal utilization changes do not invalidate an operation. The full capacity response and its separate digest still retain those observational counters. `access.vnc` becomes native only inside that same signed gate when target-config v1.2 explicitly enables it and the exact destination scope has effective `VM.Console`; endpoint discovery repeats the live gate, permissions, state digest, generation, ownership marker, and VM config digest before requesting a proxy. Snapshot, clone-as-user-action, firewall, SSH access, reservation, and placement capabilities remain unsupported.

## Gated mutation behavior

Validation accepts only isolated static-IPv4 Network resources and Linux/amd64 VM resources without mounts, arbitrary provisioning, snapshots, reset, IPv6, author MACs, or provider-managed addressing. Its closed validation plan carries only administrator profile aliases and target/capability/inventory/policy/lab digests. Per-resource planning deterministically proposes one core-owned VLAN or VMID claim, consumes dependency Network plans, derives locally administered MACs, computes bounded CPU/memory, and emits the finite full-clone step sequence.

Apply rebinds every decoded plan field to the canonical resource and configured VMID, template, storage, bridge, VLAN, hardware, disk, and ownership profiles. It rejects any stale digest, missing/extra committed claim, mismatched dependency state, substituted provider-state address, template drift, foreign destination, or permission/inventory regression before its first write. It uses only the allowlisted clone, safe config, status, guest-agent, task, lifecycle, and exact-VM delete APIs. Full ownership is placed in the clone description and checked on every later operation. Config writes use the observed PVE digest; lost responses are reconciled by exact VMID, marker, lock, task, and readback state. Cleanup never uses force, skip-lock, purge, or unreferenced-volume deletion and reports an owned leftover when absence is ambiguous.

The invocation journal uses an operator-created `0700` directory, atomic/checksummed `0600` records, file and directory sync, bounded closed JSON, and hashed filenames. It stores no token, upstream body, task log, or guest data. A mode-`0600` advisory-lock file serializes each complete apply, destroy, or lifecycle RPC across independently running provider processes; lock acquisition honors request cancellation, and process death releases the kernel lock so another process can recover from the last durable checkpoint. Multi-replica startup additionally requires this directory to be the exact `proxmox-journal` child of the verified shared artifact root. Submitted clone/lifecycle/destroy UPIDs survive restart and are polled before any action can be reissued; unknown versions, corruption, identity reuse, malformed UPIDs, ownership drift, or a terminal-result persistence failure fail closed. The conservative journal-wide lease limits one target journal to one concurrent mutation until finer resource-scoped coordination is independently proven.

## Transport and operator boundary

The client uses TLS 1.2 or newer, system roots plus the optional target CA, a fixed target origin, no environment proxy, refused redirects, bounded dial/handshake/request timeouts, and bounded response bodies. API-token calls do not use a CSRF token. Internal methods construct only the accepted fixed paths and typed form/query fields; provider values are validated before entering paths. Health reports process readiness; per-target reachability and qualification remain discovery results.

Create a dedicated Proxmox user and a privilege-separated, expiring token for this target. A mutation token uses the exact configured template, pool, storage, bridge/SDN, and node/task ACL paths documented in the mutation contract; cluster-root write ACLs are rejected. Mutation preflight requests `/access/permissions` separately for each configured path because PVE's root view omits non-propagating grants. A returned privilege key is effective at the exact requested path whether its value is `0` (not propagated) or `1` (propagated), but destination VMID-root grants and bridge grants must report `1` because writes address child VMIDs and VLAN paths. The client rejects a response for any different path. Keep the management endpoint unreachable from lab guests and expose it only to the provider process or its deployment identity.

The original 22 `TEST-PROXMOX-*` cases have executable provider bindings, including restart at every persisted mutation checkpoint and exact HTTP method/path/form assertions; `TEST-PROXMOX-023` proves target supervision inputs, protocol/features, persisted capabilities, atomic claims, dependency delivery, and absence-gated release through the control plane. `TEST-PROXMOX-024` proves the closed canonical evidence boundary, and production authorization tests additionally prove active/revoked reviewer handling plus exact build, configuration, inventory, and profile rebinding. `TEST-PROXMOX-025` through `028` cover guarded lifecycle, probe, isolation, and cross-build behavior. `TEST-PROXMOX-029` starts the current test binary as a second provider process and proves it cannot acquire the shared journal lease until the first process releases it; companion startup tests reject any multi-replica journal outside the exact shared root. Normal CI remains target-free. The disposable PVE 9.2.2 artifact is evidence for that exact testbed candidate only; each real deployment and provider build requires its own protected qualification, cleanup review, signature, and trust policy.
